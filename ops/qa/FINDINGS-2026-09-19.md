# Suite run 1 — findings (2026-09-19)

The first pointer run of `ops/qa/scenarios/suite/*.json` on a scratch network (qanet, fresh genesis: no
repositories, channels, messages or pages, nobody else online). Deployed views: wire epoch 8, ducktape-views
`a2a73e1`. **The app walked was `0.1.0+272fe780`** (setup step 5, `ducktape-launcher --version`): before #134, so
the bell there was not yet a Dialog. Evidence is `run-01/` of that run: `result.json`, `transcript.jsonl`,
`failing-tree-<scenario>-<step>.json` (paths below are relative to it). Node ids are the door's.

Six surfaces were triaged (chat, explorer, forge, huddle, inbox, palette). All six scenarios were wrong for an empty
network or for what the app offers and are fixed in the same PR; the defects below are what the trees showed on the
way. Each `##` group is one issue.

## App shell — a view's Editor is not in the tree as what it is (A1)

`app/src/view_tree.rs:4470`: `Node::Editor { label, .. } => labelled(Role::MultilineTextInput, label)`. The wire
Editor also carries `editable`, `placeholder` and the document's text; all three are dropped.

- Evidence: `failing-tree-chat-02.json`, node `console:chat/ChatView/chat/composer/editor/field`: role
  MultilineTextInput, name "", **value absent** (a TextInput beside it reports `""`), state `[focused]`, actions
  `[focus, set_value, type]`. At the same time every composer button (`…/composer/send`, `attach`, `bold`,
  `italic`, `code`, `quote`) is `disabled`, because the chat view built the composer with `editable: false` (no
  channel is open; ducktape-views `a2a73e1` chat/src/ui/chat.rs:483-486, support/composer/src/binding.rs:435).
- What is wrong: a read-only editor reports no disabled/read-only state and is offered `type`; its text is never a
  value, so nothing in the tree shows whether typing landed; its placeholder ("Message #…") is not its description.
- What a person sees: a screen reader announces an editable, unnamed text area that takes focus and silently drops
  every key. A test cannot tell "typed, Send still disabled" from "the text never arrived".
- Want: value = the editor's text (masked when private), `disabled` (or read-only) when `editable` is false, no
  `type`/`set_value` offer then, placeholder as description when there is no label.

## ducktape-views chat — a fresh network opens on a nameless room (C1)

- Evidence: `failing-tree-chat-02.json` and `failing-tree-huddle-01.json`: `console:chat/ChatView/chat/room-hash`
  "#" with no room-name node, `…/empty/name` "#", `…/empty/detail` "This is the very beginning of #. Say hello, or
  pin what the room is for.", `…/details` (Channel details) disabled, and the composer (A1) with Send, Attach and the
  format buttons disabled. The only way on is `…/new-channel` (New channel) in the sidebar.
- What is wrong: with no channel (`active_channel` empty) the room pane still draws a room: a bare `#` header and an
  invitation to say hello over a composer that cannot send. Nothing says there is no channel yet or points at New
  channel. Source: chat/src/ui/chat.rs:309-320 (header), 570-590 (empty text), 472-486 (composer enabled only with a
  channel).
- What a person sees: "Say hello" and a text box that takes focus but never sends; no reason given.
- Want: a no-channel empty state ("No channels yet" + a Create a channel action) instead of a nameless room and a
  dead composer.

## ducktape-views explorer — "No blocks yet" at block 10,984 (E1, low)

- Evidence: `failing-tree-explorer-01.json`: `console:explorer/explorer/height/text` "block 10,984" beside
  `console:explorer/explorer/empty-ledger/title` "No blocks yet".
- What is wrong: the list is the last 100 blocks that carried operations (explorer/src/host.rs:22, the filter at
  host.rs:241-260); on a quiet network it is empty while the chain has thousands of blocks. The title contradicts
  the header.
- What a person sees: "block 10,984" and "No blocks yet" on the same screen.
- Want: say what is empty, e.g. "No operations in the last 100 blocks".

## ducktape-views palette — no way to close it that the tree can name (P1)

- Evidence: `failing-tree-palette-03.json`: under `console/palette` only `console:palette/palette/input/field`
  (Search messages and pages, value "qa walk") and `console:palette/palette/note`. No Close button, and the scrim
  (`palette/scrim`, an unnamed `button_child`, palette/src/presentation.rs:29-37) is not in the tree at all.
  `result.json` palette step 3: 35 offers, "no offered action performs this step".
- What is wrong: the palette is a `Stack` with a scrim button, not an `Overlay` with a dismiss, so the app's
  Escape-to-dismiss for overlays (`app/src/view_tree.rs:2688-2700`) never sees it and the palette itself handles no
  Escape (palette/src/lib.rs handles only the chord). The only closes are a click outside the card (not addressable)
  and the open control again: Search in the rail or the chord (`on_chord_pressed` toggles, lib.rs:174-182).
- What a person sees: a pointer user clicks outside; a keyboard or screen-reader user has no Close button and
  Escape does nothing; they have to know to press ⌘K again.
- Want: an Overlay with a dismiss (Escape and the scrim), or a named Close button, and a name on the scrim.

## Door — controls under a full-window scrim are still offered (D1)

- Evidence: `result.json` palette step 3 offers and `failing-tree-palette-03.json`: while the palette's full-window
  scrim is up, the tree and the offers still hold the Pages view under it (`console:pages/pages/sidebar/new` New
  page, `console:pages/insert-3` Insert block, `console:pages/input-21474836546`, …) and the rail.
- What is wrong: the door dispatches a11y actions straight to a node, so it can press what a pointer cannot reach
  (a click there lands on the scrim and closes the palette instead). The tree has no modal or occlusion signal for a
  guest-drawn scrim, so a runner cannot tell reachable from covered.
- What a person sees: nothing different; the harm is that a walk can pass by pressing a control no person could
  press. Fixing P1 as a modal Overlay/Dialog would give the door something to scope offers by.

## Not defects (scenario was wrong; fixed in the PR)

- chat #2, huddle #1: a fresh network has no channel; Start a huddle lives in the room header of an open channel
  (chat.rs:332-343). Both scenarios now make their own channel first (`qa-chat-<walk_tag>`, `qa-huddle-<walk_tag>`).
- explorer #1: the view was in its real empty state. Block inspection needs a block with an operation in the last
  100 and the explorer cannot make one; the scenario now accepts rows or the empty ledger and walks search only.
- forge #2: an empty network has no repository and the app cannot make one (a repository comes from a git push
  through the network's Git service). The scenario now checks the empty state and its push instructions.
- inbox #1 (0.46): this device has no account (rail `Account: Sign in`), so the inbox showed `No account on this
  device` — not in the old expectation. On 272fe780 the bell kept focus (`console:rail-bell` `focused`) and there
  was no dialog node; #134 (in dev since, not in the walked build) makes it a Dialog named Notifications that takes
  focus, and the expectation now asks for that.
- palette #3: Search in the rail was offered and closes the palette (a second press of the chord); the step now
  says so. No runner change: Escape would not close this palette (P1), so a pointer-mode Escape offer would not
  help here.
